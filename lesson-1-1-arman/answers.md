# \[Part A\] 

**1. Ի՞նչ էր C10k խնդիրը, և ինչո՞ւ էին Apache-ի նման «մեկ հոսք՝ մեկ հարցման համար» մոդելով աշխատող սերվերները դժվարությամբ հաղթահարում այն։**
C10k խնդիրը մեկ սերվերի վրա միաժամանակ 10,000 և ավելի միացումներ սպասարկելու տեխնիկական մարտահրավերն էր։ Apache-ի նման ավանդական սերվերները յուրաքանչյուր նոր հարցման համար առանձին հոսք (thread) էին ստեղծում, ինչը շատ արագ սպառում էր օպերատիվ հիշողությունը (RAM)։ Բացի այդ, հոսքերն արգելափակվում էին (blocked)՝ սպասելով մուտք-ելքի (I/O) գործողությունների ավարտին, ինչը վատնում էր համակարգի ռեսուրսները և դանդաղեցնում սերվերը։

**2. Ի՞նչ նկատեց Ռայան Դալը Flickr-ի վերբեռնման առաջընթացի ցուցիչի (progress bar) վերաբերյալ, և ի՞նչ գաղափար դա նրան տվեց։**
Ռայան Դալը նկատեց, որ Flickr-ում ֆայլ վերբեռնելիս բրաուզերը ստիպված էր անընդհատ լրացուցիչ հարցումներ ուղարկել սերվերին՝ պարզապես իմանալու համար, թե ֆայլի որ մասն է արդեն վերբեռնվել։ Ավանդական սերվերները չէին կարողանում հեշտությամբ բաց պահել կապը և ինքնուրույն թարմացումներ ուղարկել։ Սա նրան միտք տվեց ստեղծել իրադարձությունների վրա հիմնված (event-driven) և չարգելափակող (non-blocking) սերվերային միջավայր, որտեղ միացումները մնում են թեթև և արագ արձագանքող։

**3. Node.js-ը չստեղծեց իր սեփական JavaScript շարժիչը։ Ո՞ր շարժիչն է այն օգտագործում, ո՞վ է այն ստեղծել, և ինչո՞ւ էր դա լավ ընտրություն 2009 թվականին։**
Node.js-ն օգտագործում է V8 JavaScript շարժիչը, որը ստեղծվել է Google-ի կողմից Chrome բրաուզերի համար և թողարկվել է 2008 թվականին։ 2009 թվականին դա հիանալի ընտրություն էր, քանի որ այն բաց կոդով էր (open-source) և JavaScript-ը դանդաղ մեկնաբանելու փոխարեն միանգամից վերածում էր արագ մեքենայական կոդի։ Սա JavaScript-ին տվեց այն արագությունը, որն անհրաժեշտ էր սերվերի վրա արդյունավետ աշխատելու համար։

**4. Ինչո՞ւ էր 2010 թվականին npm-ի ստեղծումն այդքան կարևոր Node.js-ի համար։**
npm-ի (Node Package Manager) ստեղծումը ծրագրավորողներին տվեց բաց կոդով մոդուլներ հեշտությամբ կիսելու, տեղադրելու և վերօգտագործելու հնարավորություն։ Ամեն ինչ զրոյից գրելու փոխարեն ծրագրավորողները կարող էին արագ ավելացնել արդեն պատրաստի գործիքներ իրենց նախագծերում։ Սա նպաստեց Node.js էկոհամակարգի արագ աճին և դարձրեց այն շատ ավելի հարմար իրական նախագծեր մշակելու համար։

**5. Մինչև Node.js-ը վեբը բաժանված էր «երկու աշխարհի»։ Որո՞նք էին դրանք, և ի՞նչ փոխվեց Node.js-ից հետո։**
Մինչև Node.js-ը վեբ ծրագրավորումը բաժանված էր Front-end-ի (բրաուզեր) և Back-end-ի (սերվեր), որոնք պահանջում էին բոլորովին տարբեր տեխնոլոգիաներ։ Ծրագրավորողները կլիենտական մասի համար գրում էին JavaScript, իսկ սերվերային մասի համար հիմնվում էին PHP-ի, Java-ի, Python-ի կամ Ruby-ի նման լեզուների վրա։ Node.js-ը բերեց JavaScript-ը սերվեր՝ թույլ տալով օգտագործել մեկ միասնական լեզու ամբողջ համակարգի (full-stack) համար։

**6. Բացատրեք Node.js ռեպոզիտորիայի յուրաքանչյուր թղթապանակի դերը՝ `lib/`, `src/` և `deps/`։ Ո՞ր լեզուն է հիմնականում օգտագործվում դրանցից յուրաքանչյուրում։**

* `lib/` (JavaScript) — պարունակում է ներկառուցված ստանդարտ մոդուլները, ինչպիսիք են `fs`-ը, `http`-ն և `path`-ը, որոնք ծրագրավորողները ներմուծում և ուղղակիորեն օգտագործում են իրենց կոդում։

* `src/` (C++) — Node.js-ի միջուկն է և կատարում է կամրջի (bindings) դեր՝ կապելով բարձր մակարդակի JavaScript մոդուլները ցածր մակարդակի համակարգային գրադարանների և օպերացիոն համակարգի հետ։

* `deps/` (հիմնականում C և C++) — պահում է արտաքին հիմնարար գրադարանները, որոնցից կախված է Node.js-ը, օրինակ՝ V8, libuv, OpenSSL և llhttp։

**7. Ի՞նչ է `libuv`-ն, և ինչո՞ւ են այն հաճախ անվանում Node.js-ի «սիրտը»։**
`libuv`-ն բազմապլատֆորմ C գրադարան է, որը կառավարում է ասինխրոն, չարգելափակող (non-blocking) I/O գործողությունները տարբեր օպերացիոն համակարգերի վրա։ Այն կոչվում է Node.js-ի «սիրտը», քանի որ ապահովում է Event Loop-ի աշխատանքը, կառավարում է ֆայլային համակարգի ու ցանցային խնդիրները և ղեկավարում է աշխատանքային հոսքերի ավազանը (worker thread pool)։ Առանց `libuv`-ի JavaScript-ը չէր կարողանա մեկ հիմնական հոսքի վրա սպասարկել հազարավոր միաժամանակյա գործողություններ։

**8. Նկարագրեք `fs.readFile('text.txt')` հրամանի անցած ճանապարհը երեք շերտերով՝ ձեր JavaScript կոդից մինչև օպերացիոն համակարգ և հակառակը։**
Նախ՝ `lib/fs.js`-ը (JavaScript) ստանում է ֆայլի անունը, ստուգում է արգումենտները և կանչում ներքին C++ կապը (binding)։ Հաջորդը՝ `src/node_file.cc`-ն (C++) փոխակերպում է այդ JavaScript արժեքները C++ տիպերի և հարցումը փոխանցում է `libuv`-ին։ Վերջապես՝ `deps/uv/`-ն (`libuv`-ն C լեզվով) խնդրում է օպերացիոն համակարգին կարդալ ֆայլը՝ առանց հիմնական հոսքը կանգնեցնելու, իսկ ավարտելուց հետո արդյունքը նույն ճանապարհով հետ է ուղարկում՝ ձեր JavaScript callback ֆունկցիան գործարկելու համար։

**9. Ինչո՞ւ Ռայան Դալը հետագայում ստեղծեց Deno-ն։ Նշեք մեկ տարբերություն Node.js-ից։**
Ռայան Դալը ստեղծեց Deno-ն 2018 թվականին՝ ուղղելու Node.js-ի վաղ նախագծային որոշումները, որոնց համար հետագայում զղջում էր, մասնավորապես՝ անվտանգության և մոդուլների կառավարման հարցերում։ Ի տարբերություն Node.js-ի՝ Deno-ն ի սկզբանե ունի TypeScript-ի ներկառուցված աջակցություն՝ առանց լրացուցիչ կարգավորումների անհրաժեշտության (ինչպես նաև լռելյայն ապահով է և պահանջում է հատուկ թույլտվություններ ֆայլերին կամ ցանցին դիմելու համար)։

**10. Ձեր բառերով՝ ի՞նչ է նշանակում չարգելափակող մուտք-ելք (non-blocking I/O)։ Բերեք առօրյա մեկ օրինակ (ոչ համակարգիչներից)։**
Չարգելափակող I/O-ն նշանակում է սկսել որևէ դանդաղ գործ և անմիջապես անցնել այլ գործեր անելուն՝ տեղում կանգնելու և այդ գործի ավարտին սպասելու փոխարեն։ Առօրյա օրինակ է մարդաշատ սրճարանում ուտելիք պատվիրելը. դուք դրամարկղի մոտ տալիս եք պատվերը, ստանում ազդանշանային սարք (buzzer) և գնում նստում եք կամ զրուցում ընկերոջ հետ, մինչ խոհանոցը պատրաստում է ուտելիքը՝ հերթը փակելու և սպասելու փոխարեն։

Ինչո՞ւ Node.js-ը չունի window կամ document, և ինչո՞ւ բրաուզերը չունի process։
Node.js-ը չունի window և document, քանի որ այն սերվերային միջավայր է և չի աշխատում վեբ էջերի կամ գրաֆիկական միջերեսի (UI) հետ։ window-ն ներկայացնում է բրաուզերի պատուհանը, իսկ document-ը՝ վեբ էջի կառուցվածքը (DOM), որոնք սերվերի վրա գոյություն չունեն։
Բրաուզերը չունի process, քանի որ անվտանգության նկատառումներով վեբ էջերում աշխատող JavaScript կոդին թույլատրված չէ ուղղակիորեն կառավարել օպերացիոն համակարգի պրոցեսները, շրջակա միջավայրի փոփոխականները (environment variables) կամ համակարգային ռեսուրսները։ process-ը հատուկ է Node.js-ին և տալիս է տեղեկատվություն ու վերահսկողություն տվյալ սերվերային ծրագրի աշխատանքի նկատմամբ։

B4. Ուսումնասիրեք Node.js repository


1.Բացեք lib/fs.js և գտեք այն տողը, որտեղ օգտագործվում է internalBinding('fs')։ Պատճենեք այդ տողը։ Ի՞նչի հետ է այն կապվում։

Ինչի հետ է այն կապվում. Այն կապվում է src/node_file.cc C++ բայնդինգի հետ, որն էլ իր հերթին միացնում է fs մոդուլը libuv-ի (deps/uv/) ֆայլային համակարգի գործողություններին ու օպերացիոն համակարգին:

src/node_file.cc-ի աշխատանքը. Այն կամրջում է JavaScript-ի fs մոդուլը libuv-ի ֆայլային համակարգի ֆունկցիաների հետ՝ փոխակերպելով տվյալները JS և C++ շերտերի միջև:

5 թղթապանակ deps/-ում և դրանց դերը.

deps/v8/ — Google-ի JavaScript շարժիչը, որը JS կոդը վերածում է մեքենայական կոդի և կառավարում հիշողությունը (Garbage Collection):

deps/uv/ (libuv) — Node.js-ի «սիրտը», որն ապահովում է Event Loop-ը, ասինխրոն (non-blocking) I/O-ն, ֆայլային գործողությունները և Thread Pool-ը:

deps/openssl/ — ապահովում է անվտանգ ցանցային կապերը (HTTPS, TLS/SSL) և կրիպտոգրաֆիկ ալգորիթմները:

deps/llhttp/ — գերարագ HTTP վերլուծիչ (parser), որը բայթ առ բայթ կարդում և մշակում է HTTP հարցումները:

deps/zlib/ — տվյալների սեղմման և ապասեղմման (օրինակ՝ gzip, deflate) գրադարանը:

5 մոդուլ lib/-ից backend մշակման համար.

http (lib/http.js) — HTTP սերվերներ և հարցումներ ստեղծելու ու մշակելու համար:

fs (lib/fs.js) — ֆայլային համակարգի հետ աշխատելու համար:

path (lib/path.js) — ֆայլային ուղիները (paths) ճիշտ ձևավորելու և մշակելու համար:

crypto (lib/crypto.js) — հեշավորման, գաղտնագրման և անվտանգության գործողությունների համար:

stream (lib/stream.js) — մեծ տվյալների հոսքերը մաս-մաս և արդյունավետ մշակելու համար:

C1. Կանխատեսեք հերթականությունը

տպման կարգը ADCB
Ժամաչափը (timer) 0 ms է։ Ինչո՞ւ B-ն միևնույն է անմիջապես չի տպվում։
քանի որ settimeout ը ընկնում է Macrotask queue և մինչև CallStack֊ը և իրենից առաջնահերթ queue ները չվերջանան այն չի կատարվի
քանի որ setTimeout֊ը ընկնում է Macrotasc queue(timer) իսկ Promise ները Microtask queue և Microtask queue ները ունեն ավելի բարձր կատրման առաջնորդություն։

C2. Արգելափակեք գլխավոր հոսքը
Մենք խնդրել էինք 100 ms։ Իրականում քանի՞ միլիվայրկյան սպասեց ժամաչափը։ Ինչո՞ւ։
քանի որ սինխրոն կոդը դեռ չեր ավարտվել, ու այնտեղ ցիկլ կար որը պտտվում էր 2000 անգամ արդյունքում timer ում 100ms ից հետո արդեն պատրաստ էր մակրոթասք ում cb ն բայց քանի որ ցիկլ կար, որը տևում էր 2000ms ից մի փոքր ավել։

Պատկերացրեք, որ սա վեբ սերվեր է, և busy loop-ը դանդաղ հաշվարկ է։ Ի՞նչ է լինում մյուս բոլոր օգտատերերի հետ, մինչ այն աշխատում է։
Քանի որ main thread ը զբաղված է նա չի կարող հետևել Event Loop ին այդ իսկ պատճառով սերվերը այլ հարցումներ չի կարող ընդունել այդ ընթացքում

Կապեք սա դասի հետ. ինչո՞ւ է Node.js-ը կառուցված non-blocking I/O-ի շուրջ, և ինչո՞ւ պետք է խուսափենք գլխավոր հոսքում երկար սինխրոն աշխատանքից
հենց նրա համար որ main thread֊ը միշտ զբաղվաց լինի server ի աշխատանքը ապահովելով, այսինքն հետևի Event loop ին, հարցումներ ընդունի պատասխաններ տա իսկ մնացած ծանր գործը կատարվի ասինխրոն
